# Security

## What runs where

- The gateway runs inside an **AWS Nitro enclave**: no disk and no shell. It only connects where its code and the pinned config say: KMS, DynamoDB for sealed records, Parameter Store for its config, the instance metadata service for AWS credentials, the provider APIs and your control plane. Private IP addresses are refused.
- **TLS ends inside the enclave.** Caddy runs in the enclave image next to the gateway, so the parent host only forwards encrypted bytes and never sees a key in transit. The certificate's private key and Caddy's state are sealed with the KMS key, so the host never holds them either.
- The KMS key policy denies `kms:Decrypt` to everyone, account admins included, unless the request carries an attestation document whose image hash (`PCR0`) matches the enclave image you pinned and whose `PCR16` matches the config you pinned. The enclave measures its config into `PCR16` and locks it before its first KMS call, so the same image started with another KMS key, table or control plane is refused. It denies `kms:ReEncrypt*` to everyone, so a stored share cannot be moved under another key and opened there.

## Verify the enclave

**The SDK does this for you.** Set `FIDUCY_ENCLAVE_PCR0` and `FIDUCY_ENCLAVE_PCR16` on your app server to the values your deploy printed. `PCR0` pins the enclave image; `PCR16` pins this deployment's config, so the genuine image running someone else's config (and KMS key) is refused too. Before the widget shows the key box, the user's browser asks the gateway for a fresh attestation and checks it with WebCrypto; `importKeys` does the same on your server before it sends any key. If the check fails, nothing is sent and the widget says why.

The check refuses: a document not signed through the AWS Nitro root, a document made for another request (nonce), an enclave in debug mode, an enclave running any image other than the `PCR0`s you listed, and any deployment config other than the `PCR16`s you listed. Setting `PCR0` without `PCR16` is refused before anything is sent, because the genuine image running someone else's config would pass. During an upgrade, list both values separated by a comma, then drop the old one.

Gateways on `localhost` (such as `npx fiducy dev`) are not checked. A test gateway that is not in an enclave needs `FIDUCY_SKIP_ATTESTATION=true`; the browser console warns every time. Any other gateway with neither variable set is refused.

Both values must come from your deploy output (or a release you trust), never from the gateway you are checking.

To check by hand:

```bash
curl "https://gateway.yourapp.com/attestation?nonce=$(openssl rand -hex 16)"
```

The response holds a CBOR attestation document signed by AWS. Check that:

1. the certificate chain ends at the AWS Nitro root certificate,
2. your nonce is in the document,
3. `PCR0` and `PCR16` equal the hashes your deploy printed and you locked the KMS key to.

The image holds no deployment settings, so one commit has one `PCR0` for everyone, and `PCR16` is yours alone. Today the image is still built on your host during the deploy, and two builds of the same source can differ. Images built and signed in CI, with a published `PCR0` per release, are next. You can also check a document in code with `verifyNitroAttestation` from `@fiducy/core/attestation`; it requires both `expectedPCR0s` and `expectedPCR16s`.

## Lock down the gateway hostname

The attestation check proves an approved enclave answered. It is only as strong as the rule that nobody else can get a TLS certificate for the gateway's hostname. Without that rule, someone who controls the host could get their own certificate, pass `/attestation` through to the real enclave, and serve a fake key box. Three settings narrow that gap: CAA and HSTS make such a certificate much harder to get and use, and CT monitoring tells you if one is issued anyway. They do not stop someone who controls your DNS or your AWS account: they can change the CAA record or the host. They need a hostname on a domain you control, because CAA can't be set on the default `gw.<ip>.sslip.io` name. Set `FIDUCY_GATEWAY_HOST` when you deploy; see [Use your own domain](/docs/self-hosting#use-your-own-domain).

**1. CAA: only the enclave's ACME account may get certificates.** The enclave's Caddy uses Let's Encrypt only. Its account key is sealed in the enclave, like the certificate key. After the first certificate, the gateway logs the account URL:

```bash
docker logs fiducy-enclave 2>&1 | grep 'ACME account for the CAA accounturi'
```

Add one CAA record on the gateway hostname with that URL. Put it on the gateway hostname only, not the parent domain: on the parent it would also refuse certificates for your app's own hosts.

```
gateway.yourapp.com.  CAA  0 issue "letsencrypt.org; accounturi=https://acme-v02.api.letsencrypt.org/acme/acct/123456789"
gateway.yourapp.com.  CAA  0 issuewild ";"
gateway.yourapp.com.  CAA  0 iodef "mailto:security@yourapp.com"
```

Every public CA must check CAA, so no other CA, and no other Let's Encrypt account, can issue a certificate for that name. Set the record after the first certificate exists. If you ever delete the sealed TLS state, the enclave registers a new account: update the record before it renews, or issuance fails.

**2. Certificate Transparency monitoring: see every certificate issued.** Every public certificate is logged. Subscribe to alerts for your domain (for example [Cert Spotter](https://sslmate.com/certspotter/) or [Facebook CT monitoring](https://developers.facebook.com/tools/ct/), both free). Expect only renewals from the enclave's Let's Encrypt account. Treat anything else as an incident: take the gateway offline, revoke the certificate, and check CloudTrail.

**3. HSTS: no plain-HTTP fallback.** The gateway sends `Strict-Transport-Security: max-age=31536000`, so a browser that has visited it refuses plain HTTP for a year. This header is part of the enclave image, so a deploy cannot remove it without changing `PCR0`.

## What it protects against

| Threat | Result |
| --- | --- |
| Your app server is fully taken over | Attacker can use your users' keys through the gateway until a spend limit or a freeze stops them. They can't read a key: there is no endpoint that returns one |
| A poisoned npm release of the SDK or widget | Packages publish only from this repository's `main` branch through npm trusted publishing, with provenance. Check with `npm audit signatures` |
| Your database leaks | Attacker gets handles. Useless without the enclave and your app secret |
| Fiducy's storage leaks | Attacker gets records. Useless without the handles |
| Your server logs leak | Only handles and the app secret appear; rotate the secret |
| Someone with AWS admin on the gateway account | Cannot decrypt stored keys through KMS: it refuses `Decrypt` without the enclave's attestation and refuses `ReEncrypt` always. Cannot rewrite the key policy either: only the key custodian role, assumed with MFA, and the account root user may. The attempt shows in CloudTrail as a denied `PutKeyPolicy`, and the stack emails you about it when `FIDUCY_ALERT_EMAIL` is set |
| A stolen deploy credential or GitHub token | Can build and upload a new enclave image, but the key keeps trusting the old hash until a custodian pins the new one by hand. The host never starts an image that was not pinned |
| The deploy pipeline itself (the `aws-production` job) | Can read and rotate the gateway token and run commands as root on the host through SSM. Neither opens a key: the host cannot decrypt, and a rotated token only lets the holder talk to the dashboard (see the gateway token limits). Each run needs your approval in the environment |

## Limits

- **Your app secret plus a handle can use a key** through the gateway, until a [spend limit](/docs/gateway-api#spend-limits) or a freeze stops it. Rotate the secret if it leaks.
- **No plaintext comes back.** There is no endpoint that returns a stored key to your server. The gateway proxy is the only way to use one; ask for a provider the proxy does not cover.
- **The provider sees the key**, as it always does.
- **The attestation check trusts TLS for the hostname.** It proves an approved enclave answered `/attestation`. Someone who controls the gateway's host and can also get a certificate for its hostname could relay that answer from the real enclave while serving a fake key box. [Lock down the gateway hostname](#lock-down-the-gateway-hostname) to close this.
- **Hosting**: a flaw in Nitro or KMS would break the guarantees. Self-hosting moves that trust to your own account.

## If your app is breached

Your users' keys can't be stolen from your servers, because they were never there. What an attacker with your app secret and handles can do is use those keys through the gateway. Cut that off:

1. **Freeze the app.** Dashboard, Settings, "Freeze app". The gateway refuses every AI call, key upload and import for the app at once. To freeze from your own alerting, send the app secret:

   ```bash
   curl -X POST https://your-dashboard.example.com/api/freeze \
     -H "authorization: Bearer $FIDUCY_APP_SECRET"
   ```

   The app secret can freeze its app but never unfreeze it. Only a signed-in owner can.
2. **Rotate the app secret.** Settings, "Secret and removal", "Rotate app secret". Put the new value in `FIDUCY_APP_SECRET` and redeploy. The old secret stops working at once.
3. **Unfreeze.** Your users keep their keys and rotate nothing with their provider: no plaintext key was ever on your server.

"Revoke all keys" in the same panel deletes every sealed key the dashboard has seen and makes every handle useless. Each user has to connect their key again. Use it when you are shutting the app down, or when your users must start over. A freeze already stops all use, including keys the dashboard never heard about. It and deleting an app ask for a code from your authenticator app, so set up two-factor on the Settings tab first.

## Who is responsible for what

Fiducy is open source and you run it in your own AWS account. The guarantees above hold only while both sides do their part.

**The Fiducy project:**

- the source code, the enclave image definition and the deploy scripts in this repository
- the npm packages, published only from `main` with provenance
- fixing reported vulnerabilities within the windows in [SECURITY.md](https://github.com/fiducy-dev/fiducy/blob/main/SECURITY.md)

**You, when you self-host:**

- the AWS account: MFA on the root user, a short list of people who can change the KMS key policy, CloudTrail and the alarms left on
- checking an enclave image hash before you tell KMS to trust it
- keeping the SDK, the widget and the gateway image up to date
- setting spend limits that fit your app
- freezing the app and rotating its secret when your servers are breached
- your own app: sign-in, and which user gets which handle

**Not covered:**

- use of your users' keys through the gateway while your app is compromised, up to the limits you set and until you freeze it
- a flaw in AWS Nitro Enclaves or AWS KMS
- anything done with your AWS account's root user
